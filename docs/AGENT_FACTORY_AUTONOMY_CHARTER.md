# Agent Factory 自主開發最高核心章程

> **規範級別：Agent Factory 最高核心設計原則（A-Core Doctrine）**  
> **適用範圍：Agent Factory V2、所有 A 線執行元件、所有接入工廠的模型／Agent／Runner，以及依賴工廠能力的後續產品線。**  
> **狀態：已確立為目標架構與開發方向；不代表下列尚未實作的能力已經存在或通過驗收。**

## 1. 最高使命

Agent Factory 的長期目標不是單純排程、呼叫模型或產生 Patch，而是成為一套**可持續、自主、可驗證、可恢復的 AI Software Factory**。

工廠必須逐步取得完整軟體交付生命週期的自主執行能力：

1. 理解需求、專案上下文與既有架構。
2. 規劃工作、拆解任務、辨識依賴與風險。
3. 讀取、建立、修改及重構專案程式碼。
4. 執行工具、建置、測試、安全掃描與整合驗證。
5. 分析失敗原因，提出修正並在預算與次數限制內重試。
6. 由獨立審查角色檢查設計、程式品質、安全與回歸風險。
7. 建立可追溯的變更、PR、驗收證據及交付紀錄。
8. 在明確授權與品質門檻下整合、部署、監控及復原。
9. 從成功、失敗、缺陷與維運訊號中累積知識，改善後續任務策略。

**完成定義是可重現的端到端軟體交付能力，不是模型能生成一段看似正確的程式碼。**

## 2. 對其他優先級的支配關係

本章程是 Agent Factory 的最高產品使命與架構方向。所有 A 線工作、模型接入、工具設計、任務排程、Runner 能力與品質流程，都應以提升或保護上述自主交付閉環為判斷依據。

執行順序仍固定為：

1. **A／Factory-first：** 先維持現有工廠穩定、資料狀態正確、任務生命週期完整、執行與驗收閉環可靠。
2. **自主能力建設：** 在不破壞穩定性的前提下，逐步補齊規劃、開發、工具執行、測試修復、審查及交付能力。
3. **必要 A→B 銜接：** 只處理阻擋 B 主線所需的介面、版本相容與交接證據。
4. **B 主線：** 只有在 A 的既定驗收門檻通過後，才依核准契約消費 A 的安全、唯讀投影。
5. **其他工作線：** 只在直接支援以上目標或處理已證實阻塞時介入，不得搶占 Factory 核心資源或取得其私有執行權限。

本章程**不授權**跳過既有安全政策、使用者決策權、分支保護、必要審查、資料隔離或正式環境核准；安全與資料保護限制優先於自主程度及交付速度。

## 3. 目標架構：可替換模型、可控工具、閉環 Agent

工廠應以穩定的內部契約隔離模型與執行工具，避免把核心能力綁定單一 IDE、單一模型供應商或單一 Agent 框架。

### 3.1 核心控制面（Orchestrator）

負責：
- 任務 intake、分類、優先級、拆解、依賴及派工。
- 任務狀態、lease／fencing、去重、重試、冷卻與終止條件。
- 每個任務的時間、Token、成本、輸出大小及工具呼叫預算。
- 執行上下文、檔案範圍、權限與證據的傳遞。
- 崩潰恢復、逾時處理、取消及安全重入。

控制面是唯一任務狀態與執行授權來源；Agent 不得自行偽造 lease、改寫機器管理狀態或繞過狀態機。

### 3.2 模型與推理介面（Model Provider Adapter）

- 透過統一介面呼叫本地或雲端模型。
- 可依任務難度、延遲、品質、可用資源及成本選擇模型。
- 模型可替換；切換模型不應要求重寫任務生命週期或產品核心。
- 必須記錄實際模型、版本、參數、逾時及可安全保留的執行摘要。
- 模型輸出永遠視為不可信提案，必須經過 schema、路徑、權限與政策驗證。

Ollama／Qwen 可以是目前的推理供應者；OpenCode 或其他 IDE Agent 可以是可選的執行介面，但**不得成為工廠完整自主開發能力的必要單點依賴**。

### 3.3 Developer Agent 執行引擎

工廠最終必須具備不依賴特定 IDE 的程式開發執行引擎，至少支援：
- 受限專案工作區的檔案讀取、搜尋、建立、修改及差異檢視。
- 有 allowlist、工作目錄限制、逾時與輸出上限的終端命令執行。
- Git branch、diff、commit 與 PR 提案等受控版本操作。
- 依專案任務契約呼叫測試、建置、lint、typecheck、安全掃描及其他工具。
- 對每個修改檔案記錄變更理由、任務授權及驗證結果。
- 失敗時保留可診斷證據，不得以覆蓋工作區或無限制重試解決問題。

### 3.4 多角色閉環

邏輯上至少分離以下責任；初期可由同一模型以不同受限角色執行，但驗收責任不得混為一談：

| 角色 | 責任 | 不得自行取得的權限 |
|---|---|---|
| Planner | 理解需求、拆解工作、定義驗收條件 | 不得自行授權超出任務範圍的檔案或操作 |
| Developer | 實作程式、文件及測試 | 不得自行批准自己的高風險變更 |
| Tester | 執行測試、回報可重現結果 | 不得把未執行或跳過的測試標記為通過 |
| Reviewer | 獨立檢查差異、架構、安全與回歸 | 不得因模型自評而取代獨立證據 |
| Integrator | 整合證據、建立 PR／交付紀錄 | 不得繞過分支保護或發布政策 |
| Observer／Recovery | 監控健康、診斷故障、提出恢復方案 | 不得未經授權修改正式資料或擴張權限 |

### 3.5 工具與執行隔離

- 優先使用既有 GitHub Actions、Windows Runner、Ollama 與專案既有工具，不因追求多 Agent 而平行建立重複基礎設施。
- 對不可信程式碼與模型產生的 Patch 使用受限工作區；不得讓任務任意讀取 Runner 主機秘密或其他專案資料。
- 執行環境、網路、檔案、程序、CPU／GPU、Token、時間與併發都必須有明確上限。
- 每項外部寫入、資料庫操作、套件安裝與部署都要有任務級權限及可追溯紀錄。
- Runner 是執行節點，不是任務真相來源；持久任務狀態仍由受控控制面管理。

### 3.6 外部 Neural Intelligence Agent Developer 席位

經專案負責人明確授權的外部 ChatGPT 執行席位，可作為 Factory Developer 參與任務規劃、程式實作、測試執行、有限修復及 PR 交付，但必須遵守與內建 Developer Agent 相同的任務 allowlist、檔案 owner、控制面授權、最小權限、隔離、預算及審計要求。

此席位透過目前對話中的已授權 GitHub 工具工作，不代表已成為 Factory Runner 的持久 worker、已註冊模型 Adapter 或已部署背景代理。未完成 runtime 身分、Adapter、隔離執行、任務派工、取消／逾時、審計與端到端測試前，Factory 自動呼叫此席位的能力為 NOT IMPLEMENTED。

**強制職責隔離：**
- Developer 席位負責實作與提交證據，不具有自己變更的獨立驗收權。
- GPT3 是獨立架構 Reviewer／QA，必須針對精確候選 SHA 審查架構、程式、安全、回歸及測試證據。
- Developer 不得以自測、自評、自己建立的報告或其他非 GPT3 回覆取代 GPT3 的正式審查。
- GPT3 未完成、審查者身分無法確認、證據缺失／過期或 SHA 不一致時，Fail-Closed，不得整合放行。
- GPT3 的 PASS 只表示其審查範圍內的獨立驗收結果；整合仍須滿足 CI、Branch Protection、必要人工核准及既有發布政策。

此席位不改變 GPT1–GPT5 的既有工作線 owner，也不取得控制面、Runner、Secrets、Branch Protection 或正式環境權限。

## 4. 自主能力成熟度與驗收階段

能力成熟度採以下階段管理，不得僅因某個模型能產生 Patch 就宣稱已達完整自主。

| 階段 | 能力 | 必要驗收證據 |
|---|---|---|
| A0 穩定執行 | 可 intake、派工、lease、執行、回報與恢復 | 狀態機測試、Runner 執行紀錄、重試／取消／去重證據 |
| A1 自主規劃 | 讀取專案上下文、拆解任務、列出檔案範圍與驗收計畫 | 可追溯計畫、範圍驗證、錯誤／缺漏案例測試 |
| A2 自主開發 | 在隔離工作區跨檔案讀寫、執行工具並產生可審查差異 | 真實任務 PR、檔案 allowlist、差異與執行紀錄 |
| A3 自主測試修復 | 自行執行測試、定位錯誤、有限次修復與重測 | 至少一個可重現失敗→修復→通過案例；重試上限與停止條件測試 |
| A4 多角色品質閘門 | Planner／Developer／Tester／Reviewer 職責分離並核對同一 SHA | 獨立審查紀錄、精確 SHA CI、故意植入缺陷的攔截測試 |
| A5 受控交付 | 依政策建立 PR、通過檢查後整合；部署仍依環境授權 | 分支保護、審查、回滾與部署核准證據 |
| A6 持續改善 | 分析工廠自身失敗、提出改進、以隔離 PR 驗證 | 改進前後指標、回歸測試、獨立審查及可回滾紀錄 |

**目前實際成熟度必須依最新程式碼與精確 SHA 證據重新評估。** 已知目前 Patch 產生路徑直接呼叫 Ollama；這不等同已具備完整專案工具執行、多角色獨立審查或端到端自主交付。未實作項目應標記為 NOT IMPLEMENTED／NOT RUN／BLOCKED，不得以路線圖取代實際驗收。

## 5. 自主閉環的標準流程

每個可自主處理的任務都應遵循：

1. **Intake：** 驗證來源、Issue、任務範圍、優先級及重複任務。
2. **Context：** 讀取最新 main、協作規範、handoff、相關程式碼、測試與未完成工作。
3. **Plan：** 產生結構化計畫、允許修改路徑、相依、風險、預算與驗收條件。
4. **Authorize：** 控制面驗證任務權限、檔案 allowlist、lease 與風險等級。
5. **Implement：** 在隔離工作區內執行程式修改及必要測試新增。
6. **Verify：** 執行與變更相關的測試、typecheck、lint、安全掃描及建置。
7. **Repair：** 對可修復失敗分析根因，在預算、次數及時間限制內修復；達上限即停止並回報。
8. **Review：** 由不同角色／獨立上下文審查差異與驗收證據，檢查是否有自我批准或證據偽造。
9. **Publish：** 建立分支與 PR，附上精確 SHA、測試、風險、未完成事項及回滾方式。
10. **Integrate：** 僅在既有分支保護、必要檢查與審查政策通過時合併；不因「自主」而繞過核准。
11. **Observe：** 監控 CI、部署與服務健康；故障時建立有界恢復任務。
12. **Learn：** 將去識別化且必要的失敗分類、修復結果與耗時指標寫回知識文件，供下一輪規劃改善。

任一步驟失敗，都必須留下可追溯狀態與下一個安全動作；不得將失敗吞掉、假報成功或無限重跑。

## 6. 不可自動跨越的人工核准邊界

以下事項在沒有明確、可追溯授權前，禁止 Agent 自行執行：

- 正式環境部署、正式資料庫 migration／寫入／刪除或不可逆資料操作。
- 修改 secrets、憑證、權限、身分政策、Runner 權限、網路信任或分支保護。
- 擴大任務 allowlist、解除安全隔離、關閉必要檢查或變更安全政策。
- 對外寄送訊息、付款、採購、付費 API 啟用或其他具法律／財務效力的外部寫入。
- 刪除使用者資料、清除持久狀態、跳過 lease／fencing／quarantine 或強制重跑機器管理任務。
- 將 Factory 私有狀態、Runner 控制、原始日誌、Patch 或秘密交給 B 或未授權工作線。

低風險、可回滾且已在任務授權範圍內的文件、測試與程式修改，可依既有政策自動執行；合併與部署仍須滿足專案當時有效的審查及環境門檻。

## 7. 安全、品質與真相原則

1. 模型輸出不是事實；GitHub、工作區、測試與受信任控制面紀錄才是可驗證證據。
2. 所有測試、審查、PR、CI 與部署結果都必須綁定精確 repository、branch、commit SHA、run ID 與 attempt。
3. Pending、Skipped、Cancelled、Stale、缺少或 SHA 不一致的檢查，不得視為 PASS。
4. 任何 Agent 不得自行批准自己產生的高風險變更。
5. 任務必須具備最大迭代次數、總時間、Token／成本、工具呼叫與輸出大小上限。
6. 失敗應 fail closed；不可用猜測的 lease、權限或任務狀態繼續執行。
7. 工作區修改須可檢查、可回滾；不得覆蓋其他工作者未提交的變更。
8. 工廠自身修改也必須走同一套測試、審查、證據與回滾流程；不得因為修改的是 Factory 就降低門檻。
9. 任何自主能力都不得破壞 Factory 的獨立運作或讓 B 取得 Factory 私有權限。

## 8. 目前實作與未來工作的誠實標記

每項能力必須使用下列狀態之一：
- **IMPLEMENTED：** 程式碼已存在；需附路徑與 commit。
- **TESTED：** 有實際執行的測試及結果；需綁定精確 SHA。
- **ACCEPTED：** 所有必要測試、審查與政策門檻均通過。
- **PARTIAL：** 只有部分能力或受限情境可用。
- **NOT IMPLEMENTED：** 尚無對應實作。
- **BLOCKED：** 有明確依賴、權限或環境阻塞。
- **NOT RUN／PENDING：** 尚未執行或正在等待。

任何路線圖、文件規格、模型成功回覆或單一 Patch，都不能單獨作為 IMPLEMENTED、TESTED 或 ACCEPTED 的證據。

## 9. 第一優先建設順序

在維持既有 Factory 穩定與安全的前提下，依序建設：

1. **先守住 A0：** 任務狀態、lease/fencing、排程、Runner、回報、故障恢復與精確證據。
2. **建立 A1：** 專案上下文收集、結構化規劃、任務與檔案範圍驗證。
3. **建立 A2：** IDE 無關的 Developer Agent 執行引擎與隔離工作區；OpenCode 僅可作為選配，不是必要依賴。
4. **建立 A3：** 測試執行、失敗分類、有限次修復與重測。
5. **建立 A4：** 獨立 Reviewer 與精確 SHA 品質閘門。
6. **建立 A5：** 安全 PR 整合、受控部署、監控及回滾。
7. **建立 A6：** 工廠自我診斷與受控自我改善。

任何階段若危及 A0 穩定性，先停止擴充並恢復 A0；不得為了追求「自主」而同時重寫整個工廠。
