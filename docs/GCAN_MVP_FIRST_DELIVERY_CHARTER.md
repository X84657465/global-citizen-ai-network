# GCAN P0 MVP First — 首版產品最短交付章程

> **文件狀態：** 提案／待 GPT3 獨立審查及既有治理流程接受。此文件可作為本輪開發範圍與驗收規格，但不自動變更模組 owner、工具權限、Runner 權限、正式資料權限或部署核准。
> **基準 main SHA：** `4225a244407f7a323262c4d6e17b2749193d6476`（2026-11-23 查證；只代表本輪起始點）。
> **第一版目標：** 優先交付可實際操作、可展示核心價值、可驗收的 B Product MVP；Factory 核心維持 P0，兩條工作流並行，不互相等待。
> **目標時限：** 自 MVP Issue 確認範圍與依賴起，目標 5 個工作日內完成首輪端到端驗收；若遇到外部服務、Runner、CI 或安全閘門阻塞，必須記錄精確阻塞與替代路徑，不得偽造期限達成或 PASS。

## 1. P0 — MVP First（最短時間先交付）

1. **禁止無限期建置與討論。** A–P 不得以架構擴充、文件堆疊、內部測試或工廠未全數完工為由，無限期延後第一版產品。
2. **先可用、再完整。** 優先交付可執行、可操作、可展示核心價值的最小功能集合；先確保主要使用者旅程完整，再增加進階功能、視覺精修與擴充能力。
3. **非 MVP 功能延後。** 不影響首版核心旅程、安全、資料完整性或必要可觀測性的功能，列入 Post-MVP backlog，不得阻塞首版。
4. **Factory 與 MVP 並行。** GPT1 維持 Factory 核心與必要 A→B 介面；GPT4 推進 B Product MVP。B 可使用已存在且經核對的產品 API／資料契約，或以隔離、無正式資料副作用的方式建置前端與測試。不得因 Factory 未全數完成而停止安全的 B 工作。
5. **不越過必要閘門。** 未就緒的正式 Runtime、正式資料操作、付費供應商呼叫、正式部署、Secrets／權限變更及不可逆操作，仍受原有核准與安全政策限制。MVP First 不等於取消安全閘門。
6. **明確期限。** MVP DRI 必須在 Issue 記錄 kickoff、目標日期、依賴、風險與 fallback。預設首輪目標為 kickoff 後 5 個工作日；每次延期都要記錄原因、影響、縮小範圍或改派方案。
7. **交付優先於文件完成。** 文件、原型、架構圖、假資料畫面不算產品交付；至少要有真實可執行的使用者流程、必要測試及可重現驗收步驟。
8. **交付後迭代。** MVP 通過首輪驗收後，立即依使用者回饋、錯誤率、延遲、成本與安全觀測進入迭代，不必等待 A–P 所有工作線完工。

## 2. GCAN B Product 首版範圍

### 2.1 首版核心使用者旅程

1. 訪客可理解 GCAN 的產品定位、首版能力、限制及入口。
2. 使用者可進入註冊／登入流程；未登入使用者不得讀取會員資料。
3. 已登入使用者可進入 AI 工作空間。
4. 使用者可建立、檢視及管理自己的專案。
5. 使用者可建立對話、查看歷史對話並送出訊息。
6. 在管理員完成供應商、伺服器端金鑰、預算與安全設定後，使用者可經受控 API 使用 AI 對話。
7. AI 請求須具備成本預檢、冪等鍵、重試／待處理恢復及明確錯誤狀態；不得因重送造成重複計費。
8. 使用者資料依既有身份驗證、owner 範圍及 RLS 邊界隔離；不得讓 B 產品直接讀取 Factory 私有狀態或 Runner 權限。

### 2.2 明確不列入首版阻塞範圍

多節點／聯邦運算、公開貢獻市場、獎勵支付、完整全球 Agent 市集、進階分析、完整自癒、自動正式部署、全自動工廠自我修改、非必要重構及非必要動畫／視覺效果。這些列入 Post-MVP，除非其中某項是首版安全或核心旅程的必要依賴。

### 2.3 現有程式基線（不得冒充已上線）

在基準 main 已可查到：
- `app/workspace/page.tsx`：Supabase 設定與使用者登入閘門。
- `app/workspace/workspace-client.tsx`：會員工作區、專案／對話載入、AI 請求狀態及待處理請求恢復。
- `app/api/conversations/route.ts`：登入後的對話讀取與建立。
- `app/api/ai/chat/route.ts`：登入驗證、對話權限檢查、請求冪等性、成本預檢及受控供應商呼叫。
- 對應的 workspace 與 API 測試已存在。

上述只證明程式碼存在於該 SHA；不代表本輪最新 SHA 的 CI 已通過、正式資料庫已可用、AI 供應商已啟用、Vercel Preview 已 READY 或產品已正式上線。每輪必須重新驗證。


## 2.4 A–P 全工作線都必須各自交付產品級 MVP（Portfolio MVP First）

**修正總原則：GCAN 的 MVP 不是只有 B Product 一個。A–P 每一條工作線都必須有自己可實際使用、可展示、可測試、可驗收的產品級 MVP。** B 是 GCAN 面向使用者的整合產品，不是 A、C–P 的替代品；A–P 各線交付的產品／能力，再依版本化契約整合成更完整的 GCAN 生態系。

### 定義與硬規則

1. **每線一個可用 MVP：** A、B、C……P 每條線都要定義明確使用者／消費者、核心問題、最小功能、輸入／輸出、介面、可執行成果、測試及驗收標準。不得只交文件、架構圖、成熟度數字、空殼頁面或只有 TODO 的 API。
2. **產品形式不必相同：** 面向終端使用者的線可交付網站／App／工作區；平台與基礎能力線可交付可安裝／可呼叫的服務、API、CLI、SDK、Gate、Connector、Dashboard 或可重現工作流。只要有明確使用者、可執行核心旅程、穩定契約及驗收證據，即屬產品級 MVP。
3. **各線獨立成立，整合逐步發生：** 每條線的 MVP 必須能在其核准邊界內獨立展示核心價值；跨線整合以版本化 API／事件／資料契約進行。不得要求所有線先完成才允許任何一線交付，也不得用 B 首頁展示代替其他線的產品成果。
4. **最小而非完整：** 每線只先做一條端到端垂直切片（Vertical Slice）；非必要功能列入該線 Post-MVP。不得為了「全線都有 MVP」而複製基礎設施、擴增常駐服務、引入未核准費用或跳過安全閘門。
5. **依賴排序不等於取消交付義務：** 有依賴的線先交付不依賴部分的隔離 MVP／測試版／模擬契約；依賴未通過時標示 BLOCKED 與解除條件，不得假裝正式整合完成。L 等高風險／聯邦能力可先交付隔離沙箱 MVP，不得因此開放正式跨租戶或跨組織資料交換。
6. **單一 owner、獨立驗收：** 每條線有唯一模組 owner／DRI；GPT1 負責 A–E、GPT2 負責 F–P，GPT4 負責 B 產品整合與產品需求，GPT3 獨立審查高風險／跨模組成果，GPT5 僅在明確授權範圍支援。角色不能互相取代。
7. **產品 MVP 的最低 DoD：** 有可執行的核心使用旅程、實際輸入與輸出、使用者／呼叫端可理解的錯誤狀態、必要身份／權限／資料邊界、可重現測試、使用說明、版本化契約、精確 SHA 與 owner 接受；高風險／跨模組項目另需 GPT3 獨立 Review。
8. **時限與排程：** 每條線 kickoff 後以 5 個工作日內交付第一個可展示 MVP 垂直切片為目標；端到端整合另按依賴圖排程。若無法達成，必須縮小切片、改派、拆解或標記 DEFERRED，並記錄根因與新的明確日期。
9. **狀態不得混淆：** PLANNED → IMPLEMENTED → TESTED → VERIFIED → ACCEPTED → RELEASED。每條線分別報告；不得以某一線（包括 B）已交付，宣稱 A–P 全體完成。
10. **Factory-first 的正確含義：** 保護 A／Factory 的核心工程優先級與穩定性；不代表其他線只能等候。可獨立進行的 MVP 工作應並行，Factory 以既有能力支援產品生產，不得成為全域產品交付的單一瓶頸。

### A–P 產品級 MVP 交付目錄（每線一個獨立交付物）

| 線 | 產品／能力 MVP 必須呈現的最小可用價值 | 最小可驗收成果（示例，不代表已實作） |
|---|---|---|
| A — Agent Factory V2 | 將核准任務安全轉為候選程式變更 | 一條可重現 Issue→Plan→隔離執行→Test→Draft PR→獨立 Review 的工廠工作流 |
| B — GCAN Product | 讓會員完成 GCAN 核心使用旅程 | 訪客入口→登入→工作區→專案→對話→受控 AI Chat |
| C — Predictive Coding | 提供可測試的預測編碼能力 | 可輸入明確任務／樣本、產生預測或編碼結果，並回傳可比較評估 |
| D — Deep Neural | 提供可呼叫、可評估的深度神經能力 | 最小模型／推論流程、固定測試集、品質與資源量測 |
| E — Deep Research | 將研究問題轉為可追溯研究成果 | 來源擷取→解析→主張／引用→交叉核對→可重現報告 |
| F — Security & Defense | 提供可執行的安全檢查與風險結果 | 可呼叫安全 Gate／掃描報告、明確阻擋規則與測試案例 |
| G — Release, QA & Integration | 提供可重現的發布品質放行流程 | 精確 SHA 必要檢查、相容性／回歸結果與 release decision |
| H — Observability | 讓使用者追蹤一次工作流的健康、延遲與錯誤 | request/job correlation、可查詢事件與最小儀表板／報告 |
| I — External Integration | 讓核准外部服務可安全接入 | 至少一個 mock／sandbox connector，具 schema、timeout、retry、idempotency |
| J — Resilience | 將故障轉成可驗證的診斷與修復建議 | 故障案例→根因證據→dry-run 修復方案→人工核准／回滾 |
| K — Knowledge | 讓使用者能檢索有來源的專案知識 | 文件登錄→索引→檢索→引用／來源回鏈與更新測試 |
| L — Federation | 提供隔離節點間的受控協作 | 僅在 sandbox 以兩個隔離節點完成身分、委派、驗證、撤銷及稽核 |
| M — Compliance & Risk | 將控制要求轉為可追蹤的風險狀態 | 控制項／證據登錄、風險登記、缺口報告；不宣稱法律認證 |
| N — Product Analytics | 讓產品 owner 看見經核准的聚合產品指標 | 隱私最小化事件→聚合 KPI→資料品質與來源可追溯報告 |
| O — Lifecycle | 管理版本相容、棄用與升級 | 版本登錄、支援期限、相容性檢查、遷移／回滾指引 |
| P — Governance & Trust | 將治理規則轉為可查驗的信任與審查流程 | 權限／Review 證據收集、政策評估、明確放行／拒絕結果 |

以上目錄是每線 MVP 的產品驗收方向，不代表程式已存在或已通過測試。實際實作必須先盤點該線現有程式、重用已存在能力，再補最小缺口；任何線的正式啟用仍須通過其自身安全、資料、依賴與核准閘門。


## 3. 五 GPT 分工閉環

| 角色 | 唯一主責 | 本輪硬性交付 | 邊界 |
|---|---|---|---|
| GPT1 — Factory 首席工程 | A–E，P0 主責 A Agent Factory V2 與必要 A→B Factory-side 契約 | 可執行 Factory 程式、回歸測試、精確 SHA CI 證據、穩定的唯讀交接契約 | 不接管 B 產品 owner；單次主導一項核心任務 |
| GPT2 — 專業能力工程 | F–P，僅處理直接阻擋 Factory／MVP 或必要安全、QA、觀測、整合能力 | 可執行檢查、Gate、監控指標或實際整合與測試 | 不平均灑資源、不任意改 A–E／B 核心；單次主導一項必要任務 |
| GPT3 — 獨立架構與品質放行 | 跨模組架構、安全、資料邊界、PR 差異與獨立 QA | 綁定精確 SHA 的 APPROVE／REQUEST_CHANGES／BLOCKED 結論、風險分級與缺口清單 | 不審查自己開發的成果；低風險工作採比例化審查 |
| GPT4 — B Product 負責人 | 產品方向、需求、UX、前後端/API／資料契約與 MVP 交付 | 可運作首版產品、使用者旅程、測試、產品驗收與 Post-MVP 排序 | 不直接操作 Factory 私有狀態；單次主導一項首版任務 |
| GPT5 — 全域營運與第二執行席 | 狀態／SHA 盤點、Issue／PR／CI／Runner 追蹤、派工、阻塞清理、跨線整合及受授權支援開發 | 最新狀態快照、阻塞處置、支援程式／測試／整合成果 | 不搶模組 owner、不審查或批准自己成果；僅在明確任務授權、allowlist 與工具權限內寫入 |

**角色權限說明：** 上表是責任分工，不代表任何 GPT 自動獲得 GitHub、Runner、資料庫、Secrets、部署或付費權限。GPT5 的第二執行席必須遵守現行已核准權限及 task allowlist；本提案不把 PROPOSED 治理文字當成權限授予。

## 4. 工廠優先與產品並行

1. GPT1 對 Factory P0 保有最高工程優先權，先處理任務狀態、排程、lease／隔離、Runner、恢復與 CI 證據等核心風險。
2. GPT4 同步交付 B MVP；允許先完成首頁、登入導引、工作區 UX、契約、mock／fixture 測試與已就緒 API 整合。
3. A→B 僅透過明確版本化、唯讀、最小權限契約；B 不得讀取 Factory 私有資料、lease、Runner 或執行控制權。
4. Factory 未就緒時，B 可持續進行不依賴該能力的工作；依賴部分標記 BLOCKED 並繼續其他工作。
5. 禁止以「Factory First」解讀成「B Product 必須等 Factory 全部完工」；也禁止以「MVP First」解讀成跳過 Factory 安全、資料或執行閘門。

## 5. 防空轉、阻塞與失敗處置

1. `PENDING`、`0 Job`、`SKIPPED`、`CANCELLED`、`UNKNOWN`、Rate Limit、手動暫停或生成中斷均不得視為完成、通過或健康恢復。
2. 所有 CI／Review／Preview 證據必須綁定候選 PR 的精確 HEAD SHA；SHA 更新後重新驗證。
3. 同一根因連續失敗 2 次，停止盲目重試，轉為根因分析、縮小範圍、替代路徑或升級處理。
4. 阻塞超過 1 個工作週期，必須拆解、改派、升級或標記 `DEFERRED`，並提供解除條件。
5. 任何 PR 多次修改同一檔案時，先確認唯一實作 owner；重複／衝突變更先收斂，不得平行覆蓋。
6. 自我審查、文件存在、commit 數量或測試數量都不能取代必要的獨立審查與實際測試。

## 6. 首版 MVP 驗收標準

首版驗收必須對同一候選 SHA 留下以下證據：

- [ ] 乾淨安裝與鎖定依賴成功。
- [ ] 單元／整合測試成功，並列出實際命令、測試數與失敗數。
- [ ] TypeScript、Lint、Production Build 成功。
- [ ] 訪客／未登入請求被正確拒絕或導向登入。
- [ ] 已登入使用者可建立並載入自己的專案與對話。
- [ ] AI 未設定時明確回報服務未啟用，不發出付費供應商請求。
- [ ] AI 設定完成後，能完成一次端到端對話；成本預檢、冪等性、重試與待處理恢復測試通過。
- [ ] 使用者 A 無法讀取或修改使用者 B 的專案、對話與訊息。
- [ ] 主要頁面桌面／手機版可操作，表單、導覽與錯誤訊息可存取。
- [ ] 候選 SHA 的必要 CI jobs 全部 terminal SUCCESS；PENDING／0 Job／SKIPPED 不算通過。
- [ ] 若要求 Preview，必須同一 SHA 的 deployment READY 並完成 smoke test；Rate Limit 明確列為 BLOCKED，不得冒充成功。
- [ ] GPT3 或依現行政策授權的獨立 Reviewer 對同一 SHA 留下正式結論。
- [ ] 記錄已知限制、回滾方式、費用／配額與下一輪唯一任務。

### 驗收狀態

`IMPLEMENTED`（程式存在）→ `TESTED`（實際測試）→ `VERIFIED`（精確 SHA 與環境證據）→ `ACCEPTED`（獨立審查及產品 owner 接受）→ `RELEASED`（經核准發布）。任何缺少證據的階段標記 `BLOCKED`、`NOT RUN`、`PENDING` 或 `UNKNOWN`，不得跳級。

## 7. 首版期限、追蹤與報告

- MVP DRI：GPT4；技術執行 owner 依任務卡指定；GPT3 獨立審查；GPT5 支援營運與不衝突的執行任務。
- 目標：kickoff 後 5 個工作日內完成首輪端到端驗收；若外部依賴不可控，先交付不依賴項目並將阻塞明確化。
- 每次回報必須包含：main SHA、PR HEAD SHA、變更檔案、可運作功能、實際測試／CI 終態、Preview 狀態、阻塞根因、期限影響與唯一下一步。
- 交付指標以端到端可用旅程、驗收通過率、Lead Time、阻塞時間、回歸缺陷、成本與真實使用價值為準；Issue／commit／文件數量不作為完成指標。

## 8. 安全與不可越界事項

不得因 MVP 時限而繞過身份驗證、RLS、租戶隔離、成本上限、冪等性、Secrets 管理、CI、獨立審查或分支保護。正式部署、正式資料破壞性操作、Secrets／權限／安全政策變更、付費資源及不可逆操作仍依既有人工核准政策。任何安全缺口先阻擋受影響功能，並提供不依賴該功能的替代交付路徑。

**本輪基準結論：** B Product 是目前已有可供收斂程式基線的其中一線；GCAN 的交付目標是 A–P 每條線各自擁有產品級 MVP，再依契約整合。不得以 B 已有程式或首頁展示代替其他 15 條線的 MVP。
